## [0.2.0-beta.1] - 2026-10-17

### Added

- `configdirector evaluate <key> --environment <slug>` shows the value a context gets for a config in an environment, and why. It uses the evaluator the SDKs use, so the value is the one your application gets.
- `evaluate` prints the value and the rule that served it, or the default targeting rule. Then it lists each rule in order with what it tests and its outcome. A rule that did not match names the first condition that failed and the context's value for it, or the bucket a percentage rollout put the context in. A rule after the one that served the value is not evaluated, and a rule that could not be evaluated is shown as errored.
- An old key of a renamed config evaluates the config, and the output says which key is current. `--json` prints the Admin API's response as received. Nothing is recorded: an evaluation from the CLI is not SDK activity.
- `evaluate` takes the context one of three ways. `--context-kind` (default `user`), `--context-id`, `--context-name` and the repeatable `--context-trait name=value` give it option by option, and `name:=<json>` gives a trait a number, boolean, array or object value, as in `--context-trait beta:=true`. `--context-json '{...}'` or `--context-json @file` gives the whole context as a JSON object. `--saved-context <kind>:<identifier>` names a context ConfigDirector saved from SDK evaluations in that environment. Combining two of these ways is a usage error. With none, the config is evaluated for an empty context, as an SDK given none would.
- `evaluate` needs the `environments:read` permission as well as `projects:read` and `configs:read`, and `contexts:read` for `--saved-context`. It exits with 2 when no config in the project has the key, when no environment has the slug, listing the project's environment slugs, or when no saved context in the environment has the context kind and identifier. The project comes from `--project`, `CONFIGDIRECTOR_PROJECT` or `configdirector.json`, as for `scan`.

## [0.1.0-beta.1] - 2026-10-16

### Added

- `configdirector login` asks for an API token, checks that it can list your projects, and saves it for later runs where only you can read it. The token is hidden while you paste it. `configdirector login --token <token>` saves a token without asking.
- `configdirector init --project <slug>` writes `configdirector.json`, linking the current directory to one of your projects. It never overwrites an existing file.
- Every command accepts `--token`, `--base-url`, `--project` and `--json`. The token comes from `--token`, then `CONFIGDIRECTOR_TOKEN`, then the token saved by `login`. `CONFIGDIRECTOR_BASE_URL` and `CONFIGDIRECTOR_PROJECT` stand in for the other two options, and an empty variable counts as unset.
- Exit code 0 means the command succeeded, 1 means `validate` found a problem, and 2 means the command could not run: a usage mistake, a rejected token, a suspended service or an unreachable API. Errors go to stderr, so with `--json` the JSON is all that reaches stdout.
- `configdirector scan [path]` lists every place your code reads a config key through a ConfigDirector SDK or OpenFeature provider, grouped by key, with the file, the line, the SDK and the call, and the in-code default value when the call passes a literal one. It covers every ConfigDirector SDK and OpenFeature provider, including their test clients and the Java SDK's `@*ConfigValue` test annotations. Calls whose key is not a string literal, such as a variable or a key built at runtime, are listed separately as dynamic references. A call is found when its file imports the SDK, or imports a file of the repository that does, one level deep (JavaScript and TypeScript, Python, Dart and Go), so the setup module the SDK docs create is enough; Nuxt's auto-imported composables need no import. A file that imports only a ConfigDirector OpenFeature provider, or a setup module that does, does not count as importing the SDK, so a call there that merely shares a name with an SDK call, such as `preferences.getBoolean("onboarding-done", false)`, is not reported. Nuxt calls in the `server` directory next to `nuxt.config` are reported as the Nuxt server SDK, and other Nuxt calls as the Nuxt client SDK.
- `scan` reads the current directory, or only `[path]`. It skips what `.gitignore` ignores, the `node_modules`, `vendor`, `build`, `dist` and `target` directories, binary files and files over 1 MB. `include` and `exclude` in `configdirector.json` narrow it further.
- `scan` uses the `project` in `configdirector.json` when neither `--project` nor `CONFIGDIRECTOR_PROJECT` is set.
- `scan --json` prints the references for scripts and CI. `schema/scan-output.schema.json` in the package is the JSON Schema of that output.
- `scan` resolves a call that passes a constant, such as `client.getValue(NEW_CHECKOUT, false)`, to the key the constant holds, when one assignment of a string to that name is found anywhere in the scanned code: `const`, Kotlin `val`, Swift `case`, Go, Python and C# constants, and properties of object literals, enums and maps read as `FLAGS.checkoutV2` or `Flag.newCheckout.rawValue`. The output shows the constant after the call. A name assigned two different strings, an alias of another constant and a key built at runtime stay dynamic references.
- `scan` finds the project's current and deprecated keys wherever they appear as a quoted string outside SDK calls, such as in a wrapper function, a key list or a test fixture, and lists each as an indirect reference under its key, marked as a test when the file is in a test directory or has a test name. `scan` now needs the `configs:read` permission to list the project's keys. The counts at the end of the output and `--json` carry a `kind`, `direct` or `indirect`, per reference.
- `scan` finds the calls of a file that imports the client through an `index` file or a barrel library that re-exports it, up to two re-export steps: `export … from` in JavaScript and TypeScript, `export` in Dart, and relative imports in a Python package's `__init__.py`. JavaScript and TypeScript imports through a path alias, such as `@/lib/config-director`, are followed too, using `paths` and `baseUrl` from the nearest `tsconfig.json` or `jsconfig.json`, the configs it extends, or the configs it references, as in Vite's templates. Nuxt's `~` and `@` aliases work once `nuxt prepare`, a dev run or a build has generated the `.nuxt` configs.
- Swift and Go files use what other files of their Swift target or Go package declare without importing them, so `scan` now finds the calls of a file that uses a client created in another file of the same target or package, as in the Swift SDK docs where `ContentView.swift` reads the `client` that `ConfigDirectorSetup.swift` creates. A Go package is the `.go` files of one directory with the same `package` name, so an external test package such as `package shop_test` counts only through its own imports. A Swift target is a directory under `Sources/` or `Tests/` of the nearest `Package.swift`, the directory holding the nearest Xcode project, or else the file's own directory. A call that only shares a name with an SDK call is still not reported when no file of its target or package imports the SDK; in a target that does, an unrelated `value(for:)` call such as `DateComponents.value(for: .day)` is listed as a dynamic reference, which `validate` ignores.
- `configdirector validate [path]` checks every config key your code reads through an SDK against the project's configs, and exits 1 when it finds a problem, so CI fails the build before a wrong key ships. It reports a key no config has, the old key of a renamed config with its current key, an in-code default value or typed getter of a type the SDKs do not serve the config as, a client SDK reading a server-only config or a server SDK reading a client-only one, and an in-code default value the enum does not allow. A timespan is served as a number, so it is read with a number, and an enum whose values are numbers can be read with a number too. The output groups the problems by kind with the file, the line and what is wrong; `--json` adds a `findings` array to the scan's JSON, described in `schema/scan-output.schema.json`. Keys listed in `ignoreKeys` in `configdirector.json` are not checked, test client calls are checked for unknown and deprecated keys only, and dynamic and indirect references never fail the check.
